Ship arrival prediction and berth planning

A system I built on my own, from raw data to running services. It predicts when a ship will reach its berth from AIS position reports, then gives the ship a berth or a place in the queue, a requested arrival time, and a speed that avoids waiting at anchor.

Ships spend up to 9% of their time waiting at anchorage, according to IMO. A study for IMO estimated that Just In Time arrival could cut container ship fuel use and CO2 by about 14% per voyage. That needs a port that knows when ships will arrive and can tell them when to come in.

How it works, from raw reports to a berth plan

  1. Clean the data

    30 million AIS reports, with hidden missing values such as a speed of 102.3 knots turned into gaps.

  2. Find real arrivals

    Mooring events reached after real travel become 688 labelled approach voyages.

  3. Train and test fairly

    XGBoost with a distance over speed prior, tested on 36 ships it never saw in training.

  4. Serve predictions

    A Python FastAPI service rebuilds the features from a ship's position and returns an ETA.

  5. Plan the berth

    A Spring Boot API on MySQL assigns a berth or queue place, a requested arrival and speed advice.

  6. Agree the time

    The ship accepts, rejects or omits the call, and every time is exchanged as a DCSA Port Call event.

Decisions that made the difference

  • Split by ship, not by row

    Reports seconds apart are near copies, so a random split leaks answers into the test set. I split by ship, and found the same leak in a 2024 journal study's evaluation.

  • Tested what the papers recommended

    A Bi-GRU, vessel length and time of day features all came from published work. Each was measured on held out ships and dropped when it did not help.

  • Built in Just In Time arrival

    A queued ship is told the speed that brings it in when its berth is free, never below an economical speed for its type, instead of racing in to wait.

  • Fixed a silent bug between services

    Java's HTTP client tried an HTTP/2 upgrade that the Python server rejected, dropping request bodies without an error. I traced it in the server logs and forced HTTP/1.1.

  • Let the database enforce the rules

    Unique indexes allow one open allocation per berth and one open visit per ship, so two requests at once cannot double book a berth. 54 automated tests back it.

  • Followed industry standards

    Times follow IMO's estimated, requested, planned and actual types and are exchanged as DCSA Port Call 2.0 events. The alignment is partial and not certified.
